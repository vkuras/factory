# 002 – Find a task: gaps for the architect

## G1 – The search match rule contradicts the requirements
- Status: Open
- Design: `docs/architecture/002-find-a-task.md`, "Decisions": "The match is a **prefix match on the title, compared case-sensitively** (see Interfaces)... `String.prototype.startsWith`..."; "Interfaces": "`q` selects the tasks whose **title starts with** the value of `q`, compared **case-sensitively**: `title.startsWith(q)`."
- Requirement: R4, S5.2, S5.3 (`docs/requirements/002-find-a-task.md`)
- Problem: The design specifies a case-sensitive prefix match (`title.startsWith(q)`). The requirements specify the opposite on both axes:
  - R4: "A search matches when the typed text occurs anywhere in the task's title, comparing without regard to upper and lower case. 'milk' matches 'Buy Milk', 'Order milk crate' and 'MILK'." Two of those three examples ("Buy Milk", "Order milk crate") are not prefixes of the title, and none of them share the search term's case.
  - S5.2: given task "Buy Milk", searching "milk" must match. `'Buy Milk'.startsWith('milk')` is `false` (case mismatch alone already fails it).
  - S5.3: "The text may sit anywhere in the title, not only at its start", with example "Buy milk" for "milk" at a non-start position implied by the story notes ("Order milk crate" also must match per R4). `startsWith` cannot match text that isn't at position 0, so it structurally cannot satisfy this criterion for any title where the query isn't the first characters.
  Implementing the design as written (`title.startsWith(q)`, case-sensitive) fails R4, S5.2 and S5.3. Implementing the requirements as written (case-insensitive substring match) contradicts the design's explicit "Decisions" section and its "Interfaces" row for `q`, which the traceability table cites as the implementation of exactly these rows (S5.1, S5.2, S5.3, R4). This is a contradiction between the design and the requirements, not a detail left to developers, so I'm not deciding it myself.
- Blocks: All of S5 (`src/search.js`'s `matchesQuery()`, the `q` query parameter in `GET /api/tasks`, the search field in the UI, and the S5.5 no-match state, since it can't be meaningfully verified without a matching rule that actually satisfies the acceptance criteria). Also blocks the "search text + open only" combination in S6.2, since it composes with `matchesQuery()`.
- Suggestion: Change `matchesQuery()` to a case-insensitive substring match, e.g. `title.toLowerCase().includes(q.toLowerCase())`, matching R4's worked example and S5.2/S5.3 verbatim, and update the "Decisions" and "Interfaces" sections of the design to match (drop the `startsWith`/case-sensitive language). This keeps ADR-0003 (filtering inside the existing list endpoint) and QE5 unaffected: `includes` over at most 500 in-memory titles is still on the order of microseconds, so the p95 budget is unaffected.
